# 회원가입 임시 ID 방식 — 프론트 전달 문서

## 변경 목적

약관 동의 전에 회원을 DB에 저장하던 동작을 변경했습니다. 이메일 인증과 정보 입력 후에는 Redis 임시 가입 정보만 만들고, 필수 약관 동의 완료 시 회원 저장 및 로그인 토큰 발급을 진행합니다. 약관 화면에서 이탈해도 미완료 가입 때문에 이메일 중복 오류가 발생하지 않습니다.

이 변경은 기존 가입 응답과 호환되지 않으므로 백엔드와 프론트를 함께 배포해야 합니다.

## 1. 이메일 인증 API

기존 `POST /api/auth/email/send`, `POST /api/auth/email/verify` 요청과 응답은 동일합니다. 이메일 인증 유효시간(현재 발송 시점부터 5분) 안에 `/signup`을 요청해야 합니다. `/signup` 성공 시 해당 이메일 인증 내역은 소비됩니다.

## 2. 정보 입력 후 임시 가입

`POST /api/auth/signup` — Authorization 헤더 불필요.

요청 필드는 기존과 같습니다.

```json
{
  "email": "user@example.com",
  "password": "password123",
  "passwordConfirm": "password123",
  "nickname": "온에타"
}
```

변경된 응답: HTTP 201

```json
{
  "code": "SUCCESS",
  "message": "요청이 성공적으로 처리되었습니다.",
  "data": {
    "tempId": "12345678-1234-1234-1234-123456789abc",
    "expiresInSeconds": 900
  }
}
```

- 기존 `accessToken`, `refreshToken` 필드는 없어집니다.
- `tempId`를 가입 절차 상태에 보관하고 약관 화면으로 이동합니다. 이 시점에 로그인 상태로 전환하거나 토큰 재발급을 호출하지 않습니다.
- `expiresInSeconds`는 응답 시점 기준 유효시간(초)입니다. 기본 900초이며 서버 설정으로 변경할 수 있으므로 15분을 하드코딩하지 않습니다.
- `tempId`는 약관 완료 권한을 가진 민감한 임시 값입니다. 로그·분석 이벤트에 기록하지 않습니다. Bearer JWT로 사용하지 않습니다.

## 3. 약관 동의 후 가입 완료

`POST /api/auth/signup/consent` — Authorization 헤더 불필요. 기존 GUEST 토큰 대신 **요청 본문의 tempId**를 전달합니다.

```json
{
  "tempId": "12345678-1234-1234-1234-123456789abc",
  "serviceTermsAgreement": true,
  "personalInfoAgreement": true
}
```

성공 응답: HTTP 200

```json
{
  "code": "SUCCESS",
  "message": "요청이 성공적으로 처리되었습니다.",
  "data": {
    "accessToken": "...",
    "refreshToken": "..."
  }
}
```

이때만 토큰을 저장하고 로그인 상태로 전환합니다. 저장한 `tempId`와 가입 입력 상태는 제거합니다. 완료 버튼은 요청 중 비활성화해 중복 제출을 막습니다. `tempId`는 한 번만 사용할 수 있습니다.

## 4. 이탈·만료·실패 처리

| 상황 | 프론트 처리 |
| --- | --- |
| 약관 화면에서 뒤로 이동 / 가입 취소 | 임시 가입 상태를 지우고 이탈. 서버 취소 API 호출은 필요 없음. Redis 정보는 TTL로 자동 만료 |
| 가입 절차를 처음부터 다시 시작 | 이메일 발송·인증부터 재시작 후 새 `/signup` 응답의 tempId 사용. 기존 임시 가입 때문에 이메일이 차단되지는 않음 |
| 유효한 tempId를 유지한 상태로 약관 화면 복귀 | 남은 유효시간 안에 동일 ID로 동의 가능. 유효기간 연장 없음 |
| tempId 누락·만료·이미 사용됨 / 잘못된 ID | HTTP 400, `C002`. 임시 상태를 지우고 이메일 인증부터 재시작 안내 |
| 필수 약관 중 하나라도 false | HTTP 400, `C002`. 동의를 안내하고 같은 tempId로 재시도 가능 |
| 이미 정식 가입한 이메일 | HTTP 400, `C002`. 로그인 화면으로 안내 |
| 기존 GUEST 계정 로그인 또는 refresh 시도 | HTTP 403, `C005`. 기존 토큰을 지우고 회원가입 재진행 안내 |
| 서버 오류 / 통신 실패 | 무조건 처음부터 다시 생성하지 말고 상황 안내. DB 트랜잭션이 실패하면 tempId는 남은 TTL로 복구됨. 가입은 완료됐지만 응답만 유실된 경우에는 로그인으로 복구 |

에러 응답 형식은 기존 `code`, `message` 구조를 유지합니다. `C002`는 다른 입력 오류에도 사용하므로 **모든 C002를 만료로 처리하면 안 됩니다.** 서버 message와 해당 화면의 입력 상태를 함께 확인합니다. `@Valid` 오류에서는 `data`에 필드별 오류가 추가될 수 있습니다.

기존 DB에 남아 있는 GUEST 계정은 이메일 재인증 후 새 tempId로 가입을 완료할 수 있습니다. 기존 USER 계정의 이메일 중복 차단은 유지됩니다.

## 5. 소셜 가입

현재 소셜 성공 리다이렉트 경로 `/api/token-test`는 유지합니다.

- 신규 사용자 / 기존 GUEST: `/api/token-test?tempId=...&expiresInSeconds=900`
- 기존 USER: 기존과 같이 `/api/token-test?accessToken=...&refreshToken=...`

콜백에서 `tempId` 유무로 분기합니다. `tempId`가 있으면 로그인 완료로 처리하지 말고 약관 화면으로 이동해 동일한 `/api/auth/signup/consent`를 호출합니다. 소셜 신규 가입은 별도 이메일 인증 API 호출이 필요 없습니다. 소셜 임시 정보 만료 시에는 소셜 인증부터 다시 진행합니다.

현재 백엔드에 `/api/token-test` 화면 구현은 없고 기존 리다이렉트 경로만 유지한 상태입니다. 실제 앱의 콜백/딥링크 연결은 기존 연동 설정을 확인해야 합니다.

## 6. 프론트 확인 항목

1. 일반 가입 → 약관 동의 → 토큰 저장 → 로그인 완료.
2. 약관 화면 이탈 → 이메일 재인증 → 재가입 시 이메일 중복 오류 없음.
3. 만료 ID 및 이미 사용한 ID로 요청 시 로그인 상태로 전환하지 않음.
4. 약관 미동의 후 동의 재시도 가능.
5. 소셜 신규 가입은 약관 화면, 기존 USER는 로그인 완료로 분기.
6. 구버전 GUEST 계정도 재인증 후 가입 완료 가능.

## 백엔드 운영 참고

- Redis 연결이 필요합니다. 기존 `REDIS_HOST`, `REDIS_PORT` 설정을 사용합니다.
- Lua 스크립트로 임시 ID 조회·삭제를 원자적으로 처리합니다. Redis 6.2의 `GETDEL` 명령은 요구하지 않습니다.
- TTL 기본값은 900초. `auth.signup.ttl-seconds` 또는 환경변수 `AUTH_SIGNUP_TTL_SECONDS`로 변경할 수 있습니다.
- 임시 정보는 `auth:pending-signup:<tempId>` 키에 저장됩니다. ROLE은 GUEST이며 비밀번호는 해시만 저장합니다.
- 신규 회원은 약관 동의 완료 때만 DB에 USER로 저장합니다. 기존 GUEST는 기존 ID를 유지하면서 재인증한 정보로 갱신합니다. 일괄 삭제 마이그레이션은 없습니다.
- 기존 GUEST access token과 refresh token으로 보호 API를 호출할 수 없으며, GUEST의 로그인·토큰 재발급도 차단됩니다.
- 토큰 발급 정책 변경에 따라 기존 GUEST 토큰을 전제로 한 프론트와 동시 배포가 필요합니다.
